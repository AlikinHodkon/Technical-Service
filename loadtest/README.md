# Нагрузочная проверка

Инструмент — [k6](https://k6.io/) через Docker-образ `grafana/k6`, ничего дополнительно ставить на хост не нужно. Результат интерпретируется по той же Grafana, что уже поднята в проекте — метрики пишет само приложение (`/metrics`), читает их Prometheus, по ним строится дашборд. Отдельной инфраструктуры под нагрузочный тест не требуется.

## Запуск

```bash
docker compose up -d --build   # полный стек, если ещё не поднят
docker run --rm --network container:tech-service-nginx-1 \
  -e BASE_URL=https://localhost -e VUS=20 -e DURATION=40s \
  -v "$(pwd)/loadtest:/scripts" \
  grafana/k6 run /scripts/script.js
```

`--network container:tech-service-nginx-1` — k6 работает в сетевом namespace контейнера `nginx`, поэтому `https://localhost` внутри k6 попадает ровно на nginx с правильным TLS SNI (у nginx `server_name localhost`, самоподписанный сертификат). `VUS`/`DURATION` — параметры нагрузки, без правки скрипта.

Сценарий (`script.js`) — вход один раз в `setup()`, дальше смесь read-запросов от каждого виртуального пользователя: `/api/equipment`, `/api/requests`, `/api/reports/equipment-load` (кэшируется на nginx, 30с) и `/api/sites/:id/summary`.

## Результаты (на этом стенде, демо-датасет)

Прогнано два сценария — специально с разным `RATE_LIMIT_MAX`, чтобы увидеть **и** защитный механизм, **и** реальный потолок производительности по отдельности, а не один смазанный результат.

### Сценарий 1 — штатный конфиг (`RATE_LIMIT_MAX=100` за 60с)

20 VU, 40 секунд:

| Метрика | Значение |
|---|---|
| Запросов всего | 2002 |
| `200 OK` | ~79 |
| `429 Too Many Requests` | ~1468 |
| `5xx` | 0 |
| p95 латентности успешных ответов | — (недостаточно сэмплов, лимитер срезал поток) |

**Интерпретация:** при превышении лимита сервис не падает и не деградирует — он корректно отвечает `429` и продолжает обслуживать то, что укладывается в квоту. Ни одного `5xx` за весь прогон. Это видно на панели дашборда «Доля 4xx» (резкий рост) и «Доступность сервиса» (остаётся 100% — сервис жив, просто ограничивает частоту).

### Сценарий 2 — лимит временно снят (`RATE_LIMIT_MAX=100000`), ищем реальный потолок

20 VU, 40с:

| Метрика | Значение |
|---|---|
| Запросов всего | 1983 |
| `200 OK` | 100% |
| `5xx` | 0% |
| p95 латентности | 13 мс |

100 VU, 40с:

| Метрика | Значение |
|---|---|
| Запросов всего | 9918 |
| Пропускная способность | ~164 req/s |
| `200 OK` | 100% |
| `5xx` | 0% |
| p95 латентности | 15 мс |

Подтверждено через Prometheus напрямую (не только со слов k6): `sum(rate(http_request_duration_seconds_count{status_code=~"5.."}[2m]))` за весь прогон — пустой результат, то есть `5xx` не было вообще ни одного.

**Интерпретация:** p95 почти не изменился при росте нагрузки в 5 раз (20 VU → 100 VU, 33 req/s → 164 req/s) — сервис на этом масштабе данных (демо-сиды, десятки записей) работает с большим запасом, узкое место не БД и не сама обработка запроса. Чтобы найти настоящий потолок, нужны на порядки больше данных в таблицах и/или снятие искусственной паузы `sleep(0.5)` между итерациями в скрипте — за рамками этой проверки, честно фиксируем это как следующий шаг, а не делаем вид, что потолок найден.

## Как читать на самом дашборде

Во время/сразу после прогона — Grafana → дашборд «Technical Service»:
- **Интенсивность запросов** — виден всплеск на время теста.
- **Доля 4xx** — резкий рост в сценарии 1 (рабочий rate-limit), почти ноль в сценарии 2.
- **Доля 5xx** — остаётся на нуле в обоих сценариях — главный положительный сигнал: под нагрузкой сервис не ломается, он либо отвечает, либо осознанно отказывает по лимиту.
- **Время ответа p95** — заметно растёт в сценарии 1 (запросы помимо прочего платят временем на поход через весь middleware-стек даже ради `429`), остаётся низким в сценарии 2.

## Известное ограничение

Тест гоняется против демо-датасета (десятки строк в таблицах) и с искусственной паузой между запросами одного VU — это нагрузочная проверка корректности поведения (нет ошибок, лимитер работает, задержка стабильна), а не поиск предельной пропускной способности production-масштаба. Для последнего нужны: больше данных, VU без `sleep`, и, вероятно, отдельная БД-реплика для чтения.
